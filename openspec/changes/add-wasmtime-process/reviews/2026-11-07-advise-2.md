## Independent take — written before reading design, tasks, or delta

1. Pin a native, Node-free host with exactly one database Store, entered only by its owner thread.
2. Pin bounded caller admission and waiting, including a specified response when capacity or a deadline is exhausted.
3. Pin SQL text and separately encoded parameters as the request boundary, with rows, errors, and opaque lease tokens as the return/control surface.
4. Pin exclusive transaction ownership across caller awaits; holder work must progress while other callers wait.
5. Pin token retirement, nested-transaction rejection, and close behavior so stale work cannot escape into another transaction.
6. Pin session-state isolation and explicit transaction control; refuse arbitrary SQL that bypasses the lease protocol.
7. Pin one directory capability, exact artifact/runtime identity, and a defined seed-versus-reopen lifecycle; refuse silent reseeding of existing data.
8. Pin exclusive ownership of the directory across native processes; the draft's forced lock-file handling is not evidence of safe concurrent open.
9. Refuse to infer queue recovery, trap recovery, power-loss durability, or production readiness from the successful single-owner reopen spike.
10. Tradeoff: the proven host SQL boundary keeps the ORM outside the guest, but a deliberately narrow initial value/protocol surface needs explicit rejection and failure rules.

## Comparison and steelman

The amended contract answers most of the independent take. `design.md:3–7` preserves the tested native host and artifact identity; the delta's Native Wasmtime host requirement pins the in-process operations and separate parameters. One owner queue now defines admission, immediate rejection of caller nine, deadline start, canceled-request removal, serialized holder bypass, and a bounded holder backlog (`specs/wasmtime-process/spec.md:44–71`). Token retirement and fail-closed cleanup are explicit (`:73–87`). Seeded directory and one owner defines a non-destructive startup prerequisite and second-process refusal (`:27–42`). The named acceptance command and prerequisites in `tasks.md:6` make these behaviors reviewable.

The strongest argument against carrying all of my initial concerns into blockers is the deliberately small native facility. It has explicit begin/commit/rollback operations, not the neighboring JavaScript callback-scope API. I do not require a TypeScript adapter, callback `close()` semantics, the PGlite adapter's session-state policy, a general SQL type system, or ORM execution in the guest. Those would enlarge this change. The current platform and durability limits are honest, and fault injection is sufficient to test the host's response to failed cleanup without repairing the guest.

The amended wait-only timeout is also a defensible choice. A caller abandoning its queue position need not abort another caller's transaction. The separate PGlite living spec still requires timeout-driven rollback for that adapter; the proposal explicitly excludes changing it. Thus this change can choose cancellation for the native host without rewriting either neighbor. The cost is that a stalled holder can keep ownership indefinitely: the five seconds bounds a parked caller's wait, not guest execution or transaction lifetime. The design states that limitation. I do not require a watchdog or preemption for this milestone.

Two issues still prevent accepting the reconciled contract.

## Owed before acceptance

### R5 — Reconcile the executable task with the amended timeout contract

`tasks.md:5` still says a wait past five seconds **rolls the open transaction back**. `design.md:9` and the delta at `specs/wasmtime-process/spec.md:45,65–71` say the same expiry **must not roll back the holder**. An executor following the open task would violate the acceptance scenario. Update that task to require waiter cancellation/removal, a timeout error, no later dispatch, and preservation of the holder's transaction. Keep the marker `Fresh advise after preparation` open until the reconciled files receive a fresh acceptance. This is a local reconciliation, not a request to restore the old rollback policy.

### R6 — Make transaction-control mediation cover the SQL surface actually accepted

`design.md:13` and `specs/wasmtime-process/spec.md:4` name a guard for text beginning `BEGIN`, `COMMIT`, `ROLLBACK`, or `SAVEPOINT`. That is insufficient as the complete transaction-control contract: PostgreSQL also accepts `START TRANSACTION`, `END`, and `ABORT`. For example, permitting `submit(token, "END", [])` can commit while the host still regards the lease token as live; permitting a tokenless `START TRANSACTION` can open a transaction outside `begin()`. The new retirement requirement cannot repair a transition the host never recognizes.

Specify that submitted SQL cannot change transaction/savepoint state outside the dedicated operations, covering aliases and leading whitespace/comments. State whether multiple statements are rejected before execution or how every statement is checked; do not leave a prefix-only rule as the authority. A restricted single-statement surface is sufficient and does not require building a general SQL parser. Add acceptance cases for an alternate transaction command and a comment-prefixed command, showing rejection before guest dispatch and unchanged transaction/token state; cover the chosen multiple-statement policy too. This completes the earlier R1 concern, rather than adding a new transport or broader SQL feature.
