## Independent take — written before opening design.md or tasks.md

1. Pin a runtime-clean core import graph and independently loadable Node and postgres-js entries; type-only imports must not smuggle a driver into emitted code.
2. Pin a shared session surface that accepts both root databases and transaction sessions without losing the query methods core callers need.
3. Pin a usable explicit binding path for core Model callers, alongside Node ambient lookup; browser callers must not need an ambient Node hook.
4. Refuse a process-wide database fallback; missing scope must fail before any driver method, including delayed builder and association execution.
5. Pin scope capture at model, builder, clone, hydration, eager-load, and collection boundaries so later awaits cannot retarget work.
6. Pin transaction callbacks to the transaction session and a lease token that survives awaited hooks; retaining the parent database alone is insufficient.
7. Refuse nested transaction entry through either the callback scope or a retained parent scope, while distinguishing it from independent concurrent work.
8. Pin commit, rollback, token release, escaped transaction scopes, and close semantics so stale or closed scopes cannot perform driver I/O.
9. Pin Node binding lifetime and restoration across concurrent async chains; moving createActiveRecordJS must not recreate global switching under another name.
10. Accept the tradeoff of staging adapter queues and harness migration separately if this boundary exposes their required ownership contract and preserves bound eq behavior.

## Comparison and steelman

The entry split, Node-installed context reader, shared session direction, call-site inventory, and adapter deferrals answer take items 1, 2, 4, and 10 at the architectural level. Scope retention is explicitly required, answering the intent of item 5. The import check should include dynamic imports: `src/collection-proxy.ts:210` currently reaches connection.ts that way. The implementation should also exercise the package subpaths, not merely distinct source files.

The strongest case for accepting is that this is deliberately a small seam change: Drizzle owns transaction execution, postgres.js retains its pool, and the later PGlite adapter owns serialization. Those decisions are sound. Neither a new queue nor a replacement session abstraction is needed here. Exact field names, generic spelling, and private token representation can remain implementation choices. I do not require the author's design to copy the blind take.

However, the following gaps determine observable public behavior and cannot be resolved by moving imports. They need contract decisions before implementation.

## Required revisions

### 1. Specify the explicit Model binding and its precedence over ambient context

`design.md:15` specifies only the Node-installed scope reader. The explicit-scope requirement (`specs/session-boundary/spec.md:22`) passes a session to `run`, but provides no API by which a core caller binds a Model or existing subclass to the scope. The current factory takes only a table (`src/model.ts:89`). Importing the core successfully therefore does not establish how a browser caller actually uses it.

This also affects transaction correctness: `loadBelongsTo` calls the related class's static `find` (`src/associations.ts:78`), and hooks receive instances (`src/model.ts:64`). Merely retaining a scope on an instance does not specify how related classes or hook queries use the transaction scope instead of an ambient/root scope.

Pin a minimal public usage example for core-only Model binding and transaction-bound ORM work, including an awaited hook and a related-model lookup. Define when static calls capture scope and whether explicit scope or ambient scope wins. State the Node helper signatures and binding lifetime, including how the retained `setGlobalConnection` compatibility helper binds tests without reinstating a core global fallback. Add focused scenarios with scopes A and B proving delayed builders, hydrated instances, and related work stay on A, plus interleaved Node contexts and a no-scope/no-driver-call case.

### 2. Define which scope is the receiver of a forbidden nested transaction

`specs/session-boundary/spec.md:62-68` prohibits a transaction called from inside a transaction callback without identifying the receiver. `design.md:23` repeats the prohibition. These are distinct cases: calling `txScope.transaction` and calling a retained `rootScope.transaction` inside the callback. Rejecting only the child leaves the second interpretation unmet; marking the entire root busy can incorrectly reject independent concurrent transactions on the postgres.js pool.

Against my initial take item 7, a blanket retained-parent prohibition is not automatically the right contract for a portable explicit scope. The author should choose and document the receiver/context rule, not add Node ambient detection to core to satisfy my preferred wording. Make the spec, examples, and tests agree about child nesting, retained-root calls, and independent concurrent root work. No PGlite waiter queue is requested.

### 3. Finish transaction-scope lifetime and ownership semantics

`design.md:21-25` defines callback completion and adapter ownership, but does not state that the child uses the driver's transaction session, when its token becomes invalid, or what happens when a callback scope or its query builder escapes. The spec explicitly releases the token on rollback (`specs/session-boundary/spec.md:22`) but leaves successful completion implicit. `close()` exists on both root and callback scopes without defining whether the child can close the shared client or how closing a root affects an active callback.

Specify success and failure cleanup, rejection of stale child work before driver I/O, and root-versus-child close ownership. Include the behavior when transaction completion itself fails and when close encounters active work; a documented rejection policy is sufficient and need not introduce a queue. Add fake-session tests proving child work reaches the transaction session, commit follows awaited hooks, rollback and completion errors retire the token, escaped child work cannot execute, and child close cannot inadvertently shut down an unrelated root owner.
