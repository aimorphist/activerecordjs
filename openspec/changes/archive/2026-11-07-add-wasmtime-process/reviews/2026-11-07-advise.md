# Architecture review: add-wasmtime-process

> **ADVISE:** send-back

## Independent take — written before reading design.md or tasks.md

1. Pin one native process, one owner thread, one Store, and one WASI Postgres; caller threads never enter the Store.
2. Pin SQL text and separately encoded parameters as the database boundary, with explicit rows, errors, and lease identity.
3. Pin bounded admission and a holder path that cannot deadlock behind queued nonholders; serialize all guest execution.
4. Pin transaction ownership through commit or rollback, and reject expired tokens before any guest call.
5. Pin the five-second wait policy, including how rollback can finish safely when the owner is busy or the guest fails.
6. Pin one private preopen and the proven artifact versions; explain seeded-cluster startup and exclusive directory ownership.
7. Refuse to treat the reopen spike as proof of Linux support, crash/power-loss durability, production error recovery, or a working ORM integration.
8. Refuse Node on the server path, moving the ORM into the guest without new evidence, and changes to the neighboring JS adapter contracts.
9. Require acceptance evidence for parameter binding, holder bypass, timeout rollback, stale-token rejection, and separate-process reopen.
10. Tradeoff: a single owner makes transaction isolation tractable but limits throughput and lets one slow guest call delay every caller; bound or explicitly constrain that failure mode.

## Comparison and steelman

The native-host decision is supported. `design.md:3–15` pins the proven artifact and SDK, keeps the Store on one thread, chooses capacity 8, preserves holder bypass, and acknowledges the draft's defects. This answers take lines 1, 3 in part, 6 in part, and 8. The reopen delta covers the successful sequence in take line 9.

The strongest case for this small change is that it builds a native SQL facility, not the complete ActiveRecordJS server integration. The proposal explicitly excludes a TypeScript client. Nothing in the cited spike proves an ORM can execute in this host, but nothing requires that integration to land here either. I would not demand ComponentizeJS, a Drizzle adapter, a network listener, Linux CI, power-loss testing, or repairs to PostgreSQL's stubs to accept this scope. `design.md:5` appropriately identifies macOS evidence; “a Linux binary is the same source” remains a portability intention, not tested support. This narrows take line 7 rather than turning it into new work.

The remaining concerns are the host's own correctness contracts. A bounded queue with timeout-driven rollback adds behavior the spike explicitly did not test (`finding.md:60`). Naming capacity and timeout alone leaves incompatible implementations possible.

## Owed before acceptance

### R1 — Specify admission and the SQL request boundary

`specs/wasmtime-process/spec.md:21–29` sets capacity 8 but does not say what happens to caller nine, whether admission time counts toward the deadline, or how the bounded caller pool in FR15 is enforced. An implementation can cap queued entries while accumulating unlimited blocked callers. Define admission/backpressure and its bound, the deadline start, and serialized holder dispatch when the ordinary queue is full. The holder's bypass must not become concurrent Store access or an unbounded second backlog.

The delta also lacks the proposal's SQL-plus-parameters contract. Pin the native caller operations and minimal request/result shape, separate parameter encoding, and error delivery; this can be an in-process API. State how transaction-control SQL is mediated so a raw `BEGIN`, `COMMIT`, or `ROLLBACK` cannot silently desynchronize lease ownership. Add acceptance cases for saturation, holder bypass under saturation, and a punctuation/Unicode parameter delivered separately from SQL.

### R2 — Specify timeout completion and token retirement

`design.md:9–11` and the queue requirement do not distinguish a waiter expiring while the owner is idle from expiry during a guest call. They also omit removal of the expired request, rejection of late holder work, and rollback failure. Merely dropping the holder can admit another caller into an open or failed transaction; merely returning a timeout can leave the supposedly failed request queued to execute later.

Define the transition from timeout to rollback completion, which callers receive which error, and when a successor may enter. State whether the five seconds bounds waiting only or also response/cleanup, and how busy or trapped guest execution affects that guarantee. Retire tokens on commit, rollback, timeout, and terminal failure; reject stale tokens before guest dispatch. If rollback cannot establish a clean session, specify a fail-closed outcome rather than reuse. Acceptance must exercise timeout with an active holder, late token submission, a canceled waiter that never executes, and rollback/guest failure. Fault injection is sufficient for the latter; fixing the guest's stubs is not required.

### R3 — Define directory startup and ownership

`design.md:13` acknowledges forced lock-file handling, while the native-host requirement only says “preopen one data directory.” The spike uses a preinitialized cluster plus runtime resources inside that root (`finding.md:19,25,37`), not arbitrary empty storage. Specify supported startup input and non-destructive seed provisioning or an explicit preseeded-directory prerequisite. Define enforcement against a second host opening the same root, or an explicit exclusive-access precondition and its limitation. One Store per process does not by itself prevent two owners across processes. Acceptance should cover the chosen startup policy and, if enforced, second-owner rejection without disturbing the first host.

### R4 — Make acceptance cover the new behavior

`tasks.md:3–6` names an acceptance command without a concrete invocation and only explicitly calls out the reopen sequence. Specify the command and its prerequisites, then require it to cover R1–R3 plus ordinary transaction/autocommit exclusion and nested-transaction rejection. Add corresponding scenarios to the new capability delta. Keep platform and durability claims limited to what that command actually demonstrates. The neighboring living specs need no edits.
